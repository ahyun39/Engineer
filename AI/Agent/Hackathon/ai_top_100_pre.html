1. AI TOP 100

대회 소개

AI TOP 100

  • 카카오에서 주최한 AI 해커톤으로 예선전은 2026년 10월 31일 10시부터 15시까지 진행했습니다.

문제

가상의 마을에서 쇼핑몰 고객을 응대하는 AI 에이전트를 카카오톡 채널 챗봇으로 만들어서 제출하는 것이었습니다.

문제 해결

  • 에이전트가 쓸 지식은 처음에 주어지지 않고, 마을 관계자(각자 카카오톡 채널)를 직접 인터뷰해서 지식을 발굴해야 합니다.
  • 처음에는 대표 인물 한명만 공개되고, 대화 속 단서로 다음 관계자를 찾아가는 구조이며, 관계자별로 질문은 100개로 제한되어 있고, 선행 지식을 알아야 열리는 지식도 있었습니다.
  • 제출 후 운영진이 고객 역할로 시나리오 메시지를 보내 채점하는 방식이었습니다.
  • 채점 기준은 지식 발굴률, 응답 속도, 말풍선 수, 말풍선당 글자 수, 응답 정확도(운영 정책·액션 API 처리 포함)

2. 에이전트 시스템 아키텍처

카카오톡 메시지 하나가 답장이 되기까지의 흐름입니다.

블록을 눌러 보세요각 단계가 어떤 역할을 하는지 설명이 나옵니다.

설계 포인트

  • 웹훅 1초 제한: 웹훅에는 즉시 200을 주고, 백그라운드에서 LLM을 돌린 뒤 콜백 API로 답장을 하도록 했으며 메시지 ID로 중복을 처리했습니다.
  • 액션 API 40개 자동 연결: OpenAPI 스펙을 읽어 엔드포인트를 전부 LLM 도구로 등록했고 경로 값은 형식 검증 후 호출하도록 했습니다.
  • 시나리오 분리: 심사 메시지의 케이스 ID가 바뀌면 이전 대화 기록을 초기화하도록 했습니다.
  • 보안: 입력 태그 격리, 인젝션 패턴 감지, 도구 결과 속 지시문 무시, 프롬프트 유출 검사, 조회된 주소·수령인 값이 답변에 나오면 코드로 차단하도록 했습니다.
  • 안정성: 응답 마감 시간, 액션 API 재시도, Render free 플랜 슬립 방지 셀프 핑(Render의 무료 플랜을 사용했기 때문에 채점하는 동안 서버가 멈추지 않도록 계속해서 셀프 핑을 주는 방식으로 했습니다.)

Render로 서버를 처음 다뤄 보며

이번 대회에서 Render로 서버를 처음 배포해 봤습니다. Mac이 꺼져도 서버는 Render에서 계속 돈다는 점이 가장 편했고, 실제로 써보면서 배운 부분이 있었습니다.

배포 순서
테스트 통과→git push→Manual Deploy→헬스 체크→카톡으로 확인
무료 플랜은 잠든다15분간 요청이 없으면 서버가 잠듭니다. 잠든 서버는 스스로 깨어나지 못하기 때문에 서버가 5분마다 자기 헬스 체크 주소를 호출하는 셀프 핑을 넣었습니다.
push와 배포는 별개자동 배포를 꺼둔 상태로 해서 git push만으로는 반영되지 않습니다. 대시보드에서 Manual Deploy를 눌러서 배포했습니다. 제출물이 실수로 바뀌는 일은 막아 주지만 고칠 때마다 직접 Deploy를 해야해서 번거로운 부분이 있었습니다.
환경 변수는 저장만으로 끝나지 않는다키는 코드에 넣지 않고 환경 변수에 뒀는데 Save만 하면 반영되지 않고 Save, rebuild, and deploy까지 해야 했습니다.
주소를 정확히 확인하기서비스 이름이 같은 경우에는 서비스 이름 뒤에 임의 문자가 붙은 주소를 받습니다. 처음에는 이걸 모르고 그 문자가 없는 다른 사람의 서비스에 접속하려고 하다보니 오류의 원인을 파악하지 못했습니다. 웹훅 URL을 넣을 때는 Render 대시보드에 나온 주소를 그대로 복사해야 했습니다.
재시작하면 메모리가 사라진다대화 기록을 서버 메모리에 두어서 재배포하면 진행 중인 대화가 초기화됐습니다.
로그가 디버깅의 전부카카오톡 답장이 안 올 때 이유는 대부분 Render 로그에 있었습니다. 심사 중 429를 발견한 곳도 로그였습니다.

발굴률은 어떻게 올랐나

관계자 채널에서 ./status를 입력하면 질문 수와 지식 발굴률을 확인할 수 있었습니다. 제출 전 기록을 그래프로 그려봤습니다.

표로 보기
  • 첫 대화 상대인 이민준에게는 12:13까지 32번 물어보며 55%까지 올렸지만, 이후 46개의 질문을 했음에도 10포인트 밖에 오르지 않았습니다.
  • 마지막에 만난 홍보걸은 14개의 질문으로 87%까지 올랐습니다. 관계자 소개를 좀 더 일찍 받았다면 지식을 더 발굴했을 수 있었을 것 같아서 아쉬웠습니다.
  • 제출 직전 평균 지식 발굴률은 약 58%이었으며, 총 질문 수는 283개였습니다.

4. 잘 된 부분

  • 사전 준비: 웹훅·콜백·보안·셀프 핑을 대회 전에 만들어 둬서 당일 인프라 문제는 거의 없었습니다.
  • 교차 검증: 같은 사건을 관계자마다 다르게 기억했고 문서와 진술이 엇갈리는 지점이 많았습니다. 기록(로그·정본 문서)을 진술보다 우선하는 기준을 세워 정리했습니다.
  • 회귀를 빨리 잡음: 마감 직전 규칙을 보강하자 다른 고객의 수령인 정보가 답변에 나오는 회귀가 생겼고 바로 이전 버전으로 되돌린 뒤 코드로 차단하는 장치를 추가했습니다.

5. 문제가 된 것

심사 중 LLM 429

심사 중 서버 로그에 429 Too Many Requests가 반복되는 것을 목격했습니다. 분당 토큰 한도인지 요청 한도인지까지는 확정하지 못했지만 구조에서 찾은 유력한 원인을 파악해봤습니다.

  • 지식 6만 6천 자를 매 LLM 호출의 시스템 프롬프트에 통째로 넣었습니다.
  • 메시지 1개에 도구 호출 라운드가 최대 8번이고, 라운드마다 6만 6천 자를 다시 보냅니다.
  • 429를 받으면 재시도하거나 다른 공급자로 넘기는 경로가 없어 그대로 오류 답장이 나갔습니다.

답변 끊김

문장 중간에 끊기는 답이 있었고 추정되는 두 가지의 원인이 있습니다. 출력 토큰 상한(800)을 추론 토큰이 함께 쓰며 답변 공간이 모자랐을 가능성과 500자 초과를 막으려고 문자열을 무조건 잘랐던 처리입니다.

  • 관계자 답변을 하나씩 복사해 AI에게 붙이는 불필요한 시간이 너무 많이 들었습니다.

6. 입력량 비교: 호출마다 얼마나 보냈을까

메시지 하나에 LLM이 몇 라운드를 도는지, 분당 메시지가 몇 개 들어오는지에 따라 LLM에 보내는 글자 수가 얼마나 달라지는지 직접 확인해보면 제가 구현한 지식 활용 방식이 잘못되었다는 것을 알 수 있습니다.

통째로 주입
검색 방식

분당 입력량 차이:

지식을 통으로 주입 = 라운드마다 약 70,000자(지식+규칙)
검색 방식 = 상주 규칙 약 7,000자 + 검색 결과 최대 3,000자
(글자 수 기준의 대략치이며 실제 토큰 수는 측정하지 않았습니다.)

7. 지식은 이렇게 나눴어야 했습니다

6만 6천 자를 한 덩어리로 넣는 대신 매 호출에 들어가는 상주 코어와 필요할 때만 꺼내는 검색 도메인으로 나누는 구조가 적절했을 것 같습니다.

  • 섹션마다 시행일·공개 여부·연결된 섹션을 메타데이터로 붙여서 문의 접수일 기준 규정 버전을 고를 수 있게 합니다.
  • 같이 꺼내야 판단이 맞는 섹션(예: 배송 온도 기록과 수산물 중량 기준)은 교차 참조로 연결해 검색 누락을 줄입니다.

구조 비교: 통째로 주입 vs search_knowledge

지식을 검색 도구로 분리하면 시스템 전체 구조가 어떻게 다를지 봤습니다.

항목제출 버전개선 버전
시스템 프롬프트약 70,000자약 7,000자
라운드당 추가 지식없음 (이미 전부 포함)검색한 라운드만 최대 3,000자
메시지 1개, 3라운드 입력약 210,000자약 27,000자
토큰 한도 위험높음낮음 (입력 약 1/8)
요청 횟수 한도 위험라운드 수만큼거의 같음 → 재시도·예비 공급자로 대비
정확도 위험지식 누락 없음검색 누락 가능 → 목차 상주·교차 참조로 보완

글자 수와 라운드 수로 대략 계산한 것으로 개선 버전은 실제 구현해서 측정한 수치가 아닙니다.

지식을 카테고리별 지식 그래프로 그려봤습니다

60개 섹션을 상주 코어 1개 + 검색 도메인 8개로 묶었습니다. 원 크기는 섹션 글자 수, 주황 점선은 한 문의에서 함께 꺼내야 하는 교차 참조입니다.

도메인별 분할 표

검색은 이렇게 돌아갑니다

① 상주 코어

응대 원칙, 위기 대응, 이관 절차 같은 행동 규칙과 지식 목차만 매 호출에 넣습니다.

② 도메인 찾기

LLM이 search_knowledge를 호출해 필요한 도메인을 찾습니다.

③ 섹션 + 이웃

맞는 섹션 2개와 교차 참조로 연결된 섹션 1개를 최대 3,000자로 돌려줍니다.

④ 날짜 필터

시행일 정보로 문의 접수일에 맞는 규정 버전만 남깁니다.
섹션 메타데이터 예시 
{
  "id": "refund.partial_formula",
  "domain": "환불·보상",
  "title": "부분환불 산식",
  "effective": "시행일",
  "visibility": "internal",   // public이면 고객에게 인용 가능
  "keywords": ["부분환불", "하자 비율"],
  "links": ["refund.delegation", "refund.rules"]
}
다음에 구현한다면:
  1. 지식 파일을 제목 단위로 나눠 불러오고 search_knowledge를 도구로 등록합니다.
  2. 시스템 프롬프트에서 지식 본문을 빼고 섹션 목차만 넣습니다.
  3. 429는 Retry-After만큼 기다려 재시도하고 그럼에도 실패하면 예비 공급자를 호출합니다.
  4. 대표 질문 20개로 정답 섹션이 상위 3개에 드는지 테스트합니다.
  5. 공개 TC를 연달아 보내 429와 지연 속도를 측정합니다.

8. 다시 한다면

(지식 구조) 나눠서 꺼내 쓰기 상주 코어(응대 원칙·이관·안전 규칙, 약 7천 자)만 매 호출에 넣고 나머지는 도메인별로 나눠 search_knowledge 도구로 필요할 때만 꺼내기
(안정성) 실패는 코드로 대비하기
  • 429는 대기 후 재시도하고 실패했을 때를 대비하기 위해 다른 LLM을 예비 공급자로 배치
  • 답변 길이는 코드로 보장: 문장 단위로 자르기, 잘린 응답이면 다시 요약 요청
  • 제출 전 배포 서버로 연속 부하 테스트해서 한도 확인
(검증) 로컬 TC 실행 스크립트부터 만들기 대회 시작과 동시에 카카오톡이나 배포 없이 에이전트 함수를 직접 불러 답변, 도구 호출, 길이, 개인정보 노출을 검사하는 스크립트를 만들기. 수정 주기를 몇 분에서 수십 초로 줄일 수 있는 방법.
(인터뷰) 리스트 대신 단서 따라가기
  • 관계자마다 공통 첫 질문 3~4개(맡은 업무, 가진 문서, 최근 사건, 더 잘 아는 사람)로 시작하고 답변에서 단서를 뽑아 다음 질문 1~2개를 상황을 따라가며 고르기
  • 카카오톡 PC의 대화 내보내기로 관계자별 대화를 파일로 넘겨 한꺼번에 정리
  • 진술 불일치 표를 따로 관리하기. 엇갈리는 지점 자체가 숨은 지식이고, 에이전트의 우선순위 규칙이 되는 방식.
  • (규정이 금지한 것은 대량 자동 요청과 공격) 그냥 전부 손으로 입력했지만 대회 중 받은 시스템 메시지를 보면 AI 활용을 더 적극적으로 고민할 여지가 있었으며, AI 활용 허용 범위를 다음엔 시작 전에 확인하고 AI가 내 손보다 더 많이 움직이도록 하기
(카카오톡 화면 읽기) AI는 읽고, 사람은 보내기

이번에는 답변을 하나씩 복사해 AI에게 붙이는 방식으로 했지만, 다시 한다면 AI가 카카오톡 PC 앱 화면을 스크린샷으로 읽는 computer use 방식을 시도해보기. 메시지는 사람이 보내고, AI는 읽고 정리하는 역할만 맡는 방식.

사람이 질문 전송→"새 답변 왔어, 봐 줘"→AI가 화면을 읽음→관계자별 파일에 누적→단서·불일치 비교→누구에게 무엇을 물을지 제안
  • 동시에 보는 건 X: 10개 채팅방을 하나씩 돌아가며 읽습니다. 대신 파일에 쌓인 뒤에는 10명의 내용을 한꺼번에 비교할 수 있습니다.
  • 실시간 감시도 X: 요청을 받거나 정해 둔 주기에만 확인합니다. 새 답변이 왔을 때 그 방만 읽게 하는 편이 효율적입니다.
  • 원문 대조는 필요: 이미지로 읽어서 번호·날짜·금액을 잘못 읽을 수 있으니 지식의 기준은 내보낸 대화 파일로 다시 맞춥니다.
  • 문서 링크는 따로 열기: 메시지 속 링크는 주소를 확인한 뒤 브라우저에서 엽니다.
  • 규정 확인이 우선: 대회라면 화면 읽기와 자동 입력이 허용되는지 시작 전에 확인해야 합니다.

아직 카카오톡에서 직접 시험해 본 방식은 아니고, 다음에 해 보고 싶은 아이디어입니다.

(AI와 일하는 방식) 역할을 나누기

AI 세션 하나에 인터뷰 보조·지식 정리·개발·배포를 다 맡겼더니 문서에 적어 둔 배포 중심 일정에 끌려가 지식 발굴 단계를 충분히 돕지 못했습니다.

  • 아직 지식 발굴률이 50%도 올라가지 않았는데 AI가 계속해서 질문은 멈추고 배포를 하라고 질릴 정도로 방향 전환을 시도했습니다.

9. 마치며

5시간 동안 지식 발굴과 에이전트 구현을 동시에 해야 하는 대회였습니다.

처음에는 에이전트를 만들기 위한 관계자들과의 대화라고 생각하며 시작했는데, 막상 대회를 진행하다보니 점점 취조를 하는 느낌이 났습니다. 중간에 내가 AX 전문가인지 형사인지 하는 생각이 들기도 했습니다. 관계자가 처음에는 한명으로 시작해서 한명씩 한명씩 관계자의 연락처를 받거나, 새로운 파일 혹은 새로운 지식을 얻으면서 진행하니 방탈출 느낌도 났습니다.

대회 진행도 원활했고 클로드 프로 플랜으로도 지식을 파헤치는 작업과 에이전트를 만드는 작업까지 약간의 크레딧만 추가해서 만들 수 있다는 부분이 좋았습니다. 무엇보다 AI로 문제를 풀어가는 작업은 안해봤는데 이번 예선에서 5시간이 어떻게 흘러가는지 모르게 몰입할 정도로 재밌었습니다. (매달 AI로 이런 대회가 열렸으면 할 정도로 너무 재밌었습니다.)

이번 대회에서 가장 많이 느꼈던 건 제가 아직도 AI를 제대로 쓸 줄 모른다는 점입니다. 우선 심사 로그를 보며 에이전트가 지식을 어떻게 활용하도록 해야 하는지도 배울 수 있었습니다. 지금까지는 지식을 통으로 넣어서 주는 방식만 생각했는데, 이 지식을 분류해서 필요한 순간에 적절하게 꺼내쓸 수 있는 구조가 문서 크기가 컸을 때 중요하다는 것을 배웠습니다.

그리고 다른 참가자들이 AI를 어떻게 활용하면서 대회를 진행했는지를 보고 배운 부분도 많았습니다. 클로드를 쓰면서 skill은 거의 안쓰고 있었다는 것도 느꼈고, AI를 잘 쓰기 위한 방법으로 직접 많이 써보는 것도 중요하겠지만 여러 유용한 방법들을 써보는 것도 공부가 되겠다는 것을 확실하게 느꼈습니다.
